状态：设计已确认并正在新包中实施；范围为“直接编码网页 URL，接入现有 Nova 管理”。包名、命名空间和配置名采用通用名称。二维码类型支持范围由宿主配置决定，不能由 migration 决定。

## 1. 结论

当前包的图片生成能力仅支持微信小程序码，具体调用 `/wxa/getwxacodeunlimit`。不存在普通 QR Code 编码器，也没有根据二维码类型选择生成方式的机制。把网页 URL 填入现有 `page/path` 不能获得普通网页二维码。

新包无需承担旧包兼容负担。以 `fayne/laravel-nova-qrcode`、`Fayne\\QrCode`、`qrcode.php` 为正式名称，使用 `qrcodes` 表；新增本地网页码生成器，保留微信生成接口，并共用业务实体关联和 Nova 管理。不引入驱动注册系统。

| 范围 | 预计工作量 | 交付边界 |
| --- | --- | --- |
| 仅新增网页二维码生成 API | 0.5～1.5 人日 | 本地生成 PNG、Data URL、保存文件及基础测试；不接数据库和 Nova |
| 网页码接入完整现有管理流程，推荐 | 3～5 人日 | 类型、数据库、模型方法、Nova、存储、迁移及回归验证 |
| 活码、修改目标、到期停用、基础扫码统计 | 合计约 6～10 人日 | 在完整方案上增加短链接路由、停用检查和访问记录；高级报表另估 |

以上是熟悉 Laravel/Nova 的单人开发估算，不是固定报价。按一天约 8 小时、可获得测试宿主与微信测试账号、普通规模数据迁移估算；不含部署等待、正式物料设计、复杂权限改造、多租户、多微信账号以及报表平台。

## 2. 当前流程和复用范围

### 2.1 生成链路

1. 程序直接调用 `Support/Generator.php`，或经 `Traits/HasQrcodes.php` 创建业务关联记录。
2. `Generator::getQrcodeOutput()` 通过 `MiniApp` 调用微信接口，传递 scene、page、环境和微信样式参数。
3. `Generator::handle()` 保存图片，并返回文件 URL 或调用回调。
4. Trait 与 Nova Action 把图片 URL 写入 `urls`；键按宽度和微信环境组成。
5. Nova 展示记录、图片，并提供队列生成 Action。

## 3. 方案比较与推荐边界

### 3.0 包名是否需要调整

旧包曾使用 `fayne/mini-app-qrcode`、`Fayne\\MiniAppQrcode` 和 `mini-app-qrcode.php`；新包按已确认名称实现，不保留旧命名兼容层。

若包尚未对外稳定发布，建议现在改为通用名称，例如：

| 项目 | 建议值 |
| --- | --- |
| Composer 包名 | `fayne/laravel-nova-qrcode` |
| PHP 命名空间 | `Fayne\\QrCode` |
| 配置文件 | `qrcode.php` |
| 服务提供者 | `Fayne\\QrCode\\QrcodeServiceProvider` |
| 目录名 | `laravel-nova-qrcode` |

`qrcode` 已足够表达能力，避免把实现方式或某个平台写进公共名称。若担心 Packagist 名称占用，可使用 `fayne/laravel-qrcode`，但不建议再把 `mini-app` 放进新名称。

改名属于破坏性变更，影响 Composer 包名、PSR-4、服务提供者、Facade、所有 `use` 语句、配置发布路径、README、测试命名空间和宿主包引用。它不应与网页二维码功能偷偷混在一次“兼容性修复”中。建议在同一个尚未发布的大版本中完成，或者先发布一个明确的重命名版本并提供迁移说明。若包已经被多个生产项目依赖，则可以暂时保留旧名称，内部新增通用类名，等下一次主版本再重命名。

本分析后续正式采用以上新名称，不保留旧包名、旧命名空间或旧配置别名。由于这是新包，不增加兼容包装层。`allowed_types`、记录类型和运行时必填规则保持不变。

### A. 独立增加网页图片生成工具

改动最少。适合只需要代码传 URL、取得图片的场景；不解决数据库区分、Nova 创建和管理问题。如果最终需要后台，应直接选 B，避免临时绕过现有管理流程。

### B. 同表双类型、独立生成入口，推荐

保留微信 Generator；新增 `WebQrcodeGenerator`。用 `type` 区分 `wechat_mini_app` 与 `web_url`，用 `target_url` 保存网页目标。只在实际共用的文件保存处抽取小型辅助类，不建设通用驱动框架。

网页码生成全程不请求微信，也不访问目标网站。无需微信凭据即可生成网页码，但本期 Composer 仍安装原有 EasyWeChat 与 Nova 依赖。“无需凭据”和“可独立于微信包安装”是两个范围。

### C. 改成通用二维码平台

统一驱动协议、更名、可选 Nova/微信依赖、活码路由和统计适合另立任务。当前两种二维码不足以证明需要这一层架构，本期不推荐。

### 第一期明确不包含

短链接、修改已分发二维码的目标、扫码跟踪、到期拦截、Logo、海报、任意文本/Wi-Fi/名片编码、新 HTTP 生成接口，以及新的用户权限系统。

静态码保存的是 URL 本身。修改数据库或删除图片不会使已经下载、印刷的二维码改变目标或失效；目标网页自身仍可通过宿主认证或业务规则限制访问。扫码后使用哪个浏览器由扫描客户端决定，本包不保证自动跳出微信打开系统浏览器。

## 4. 推荐开发契约

以下方法名和字段是拟定契约，不代表已经存在。

### 4.0 宿主配置：允许哪些二维码类型

在 `config/qrcode.php` 使用以下允许类型配置：

```php
'allowed_types' => [
    'wechat_mini_app',
    'web_url',
],
```

配置值只表达当前项目允许创建哪些类型，不表达某条记录的类型，也不承担数据库约束。支持以下三种有效状态：

| 配置状态 | 创建界面 | 必填字段 |
| --- | --- | --- |
| 仅 `wechat_mini_app` | 不显示类型选择，默认小程序码 | `scene`、小程序 `path` |
| 仅 `web_url` | 不显示类型选择，默认网页二维码 | `target_url` |
| 同时包含两者 | 先选择二维码类型，再显示对应字段 | 按所选类型动态决定 |

空数组、未知类型、重复值都应在配置解析或服务提供者启动时失败，并给出明确配置错误；不要让项目运行到创建记录时才出现隐含错误。建议提供 `allowedTypes()` 和 `supportsType(string $type)` 这类只读配置访问方法，避免在 Nova、Trait、Action 中各自解释配置。

这项配置是项目级策略，不能仅依赖 Nova 隐藏字段。所有创建、更新、生成 Action 和业务 Trait 都必须在服务端再次检查：类型必须在 `allowed_types` 中，且所选类型的字段满足对应规则。若项目从“两者都支持”改为单一类型，已有另一类型记录应继续可读和可管理；默认策略是禁止新建及重新生成不再允许的类型，不自动删除历史图片或数据。是否允许编辑旧记录目标，需要另行确认。

配置变更不需要 migration，也不应通过迁移脚本写入数据库。部署配置后应清理配置缓存，并用宿主实际配置做一次 Nova 创建和代码调用验收。

### 4.1 数据模型

| 字段 | 微信小程序码 | 网页二维码 |
| --- | --- | --- |
| `type` | `wechat_mini_app`，现有数据默认值 | `web_url` |
| `scene` | 按现有微信规则必填、唯一 | NULL，不制造无用 scene |
| `path` | 小程序 page | NULL |
| `target_url`（新增 text） | NULL | HTTP/HTTPS 绝对 URL，必填 |
| `urls` | 保留现有 `宽度_环境` 键 | 使用 `宽度_web` 键，例如 `430_web` |
| `expired_at` | 保留现有元数据语义 | 不显示为可使静态码失效的设置 |

第一期网页码固定黑色前景、白色背景、PNG、固定纠错等级与静区，只开放宽度。因此一个宽度对应一个网页图片，暂无须设计多样式变体表。以后开放颜色、Logo 或格式时再扩展变体标识。

migration 只提供两种类型的联合字段结构：`type`、可空的 `scene`、可空的微信 `path`、可空的 `target_url`。它不能根据 `allowed_types` 把任何列设为 NOT NULL，也不能在数据库层要求“scene 与 target_url 二选一”，因为该策略属于应用配置且可能随部署改变。应用层必须保证：小程序记录要求 scene/path，网页记录要求 target_url；不允许同时填入互相无关的字段。

类型创建后不可直接切换；数据库更新入口和 Nova 均执行该约束。网页目标改变时，清空该记录当前 `urls`，明确要求重新生成；已经分发的旧图仍指向旧目标。无自动删旧文件任务。

迁移必须支持空库安装与已有数据升级：新增 type、target_url，scene 改 nullable 并保留唯一约束。现有 scene 不强制转格式。当前 scene 使用 uuid 列但业务按不超过 32 字符的字符串使用；开发时核实宿主数据库实际列类型，勿把数据库 UUID 原生类型兼容承诺带入此次估算。

特别注意：Provider 检测到宿主已发布建表迁移后，会跳过整个包迁移目录。只添加一个迁移文件可能不会被既有宿主发现。必须明确区分旧建表迁移去重与新升级迁移注册，并测试“已发布旧迁移”“未发布旧迁移”“全新安装”三种情况，防止重复建表或漏升级。

回滚新增迁移会丢失网页目标，且现有网页行的 NULL scene 无法直接恢复为 NOT NULL。推荐先导出网页数据、删除或迁移网页行，再允许回滚；不自动删除业务行、不填伪造 scene。升级前备份，先部署数据库扩展，再部署新代码及重启队列。

### 4.2 程序接口

- 旧 `Generator::handle()`、`getQrcodeOutput()` 和 `generateQrcode()` 保留参数名、调用方式及微信语义，尤其保留命名参数和 dataUrl 调用。
- 新 `WebQrcodeGenerator::getQrcodeOutput()`：输入 URL、宽度和输出类型；输出限定 PNG 字节或 PNG Data URL，默认字节；不照搬微信 json/psrResponse。
- 新 `WebQrcodeGenerator::handle()`：输入 URL、磁盘、目录、宽度；成功返回图片 URL。新方法不引入可改变返回类型的回调。
- 新 `HasQrcodes::generateWebQrcode()`：输入名称、URL、additionalData、宽度、存储选项；创建业务关联记录，固定返回持久化后的 Qrcode 模型，图片地址从 `urls` 获取。
- 新网页记录生成失败时不留下看起来已完成的业务记录；先生成并成功存储，再在数据库事务中创建记录。数据库失败可能留下孤立图片，作为已知限制记录，不误删内容寻址的共享图片。
- 已有记录经 Action 重新生成时，只在图片成功写入后更新 `urls`；失败不写入虚假地址。

### 4.3 输入与存储

- 公共网页生成入口和 Nova 使用相同 URL 约束：仅 HTTP/HTTPS、完整域名或 IP 主机、禁止控制字符和 URL 用户名密码；建议最大 2048 字节，超限明示报错。此为产品限制，不是二维码容量的保证。
- 保留合法 URL 的查询参数、百分号编码及 fragment，不静默重排或解码。国际域名由调用端提供标准可编码 URL。
- 不请求目标 URL 做可达性验证；网络可达性由扫码客户端决定。
- 宽度第一期沿用后台范围 280～1280，默认 430；编码器保留标准静区和完整模块。因模块取整造成的实际尺寸差异在接口文档说明；长 URL 超出可用容量或尺寸时返回清晰错误，不能裁剪静区硬凑像素。
- 存储必须使用选定 disk 的 `put` 和 `url`，并检查写入结果；未显式指定磁盘时使用包默认 public，目录默认 `images/qrcodes`，允许宿主配置覆盖。
- 网页文件使用 `.png` 和正确 MIME。文件指纹包括 type、完整目标、实际渲染参数和格式；微信文件指纹至少补入 page，避免同 scene 不同 page 覆盖。
- `urls` 继续表示可展示图片链接；私有磁盘签名链接不是本期范围，验收磁盘需提供浏览器可访问地址。
- 原有微信流读取与格式问题先加回归覆盖，再调整；不要将微信 response 对象塞入网页码存储流程。

### 4.4 Nova

- 新增类型选择与类型筛选；类型选择是否显示由 `allowed_types` 决定。单类型配置下直接固定类型并隐藏选择器；双类型配置下先选择类型，再显示对应字段。
- 微信显示 scene/path，使用微信校验；网页显示 target_url，禁止调用 `valid_mini_qrcode`。必填规则必须在服务端与表单端保持一致。
- 生成 Action 拆成微信与网页两个入口；网页只收宽度、disk、目录，无 env、check_path、auto_color 等微信字段。
- Action 服务端逐条验证模型类型，不能仅依赖 UI 隐藏；混合类型批量选择在执行前整体拒绝并给出提示。
- 预览兼容现有键和新 `宽度_web` 键；显示“网页”而非微信环境。所有 URL 和标签经过 HTML 转义。
- 保留宿主现有授权约定，不新增公开生成路由。当前 Policy 多数操作返回 true，不能宣称已有细粒度权限；如需限制运营人员创建或生成，单独明确宿主策略与验收。

### 4.5 依赖建议

候选使用 `endroid/qr-code`，只使用 PNG Writer 与 Data URI 能力。其官方项目说明支持 PNG 输出，PNG 需要 GD。5.1.0 的官方依赖文件要求 PHP ^8.1，可覆盖本包 PHP ^8.2 下限；当前主分支要求 PHP ^8.4，不能直接据主分支示例升级本包最低 PHP 版本。

开发开始时以实际发布版本和 Composer 解算选择受支持版本；5.1.0 这里只作已核验的兼容候选，不是完成安装验证或维护状态保证。本次未安装依赖、未改 composer.json。若维护策略要求新版，应显式评估抬升 PHP 下限，不悄悄改变。

## 5. 现有问题：影响范围与证据强度

以下为源码检查，不等同于已在生产复现。

| 发现 | 证据与影响 | 本次处理建议 |
| --- | --- | --- |
| 写盘参数使用不正确 | Generator 第 34 行 `Storage::put(..., $disk)`；宿主 FilesystemAdapter 第三个参数是 options，字符串按 visibility 处理，不用于选择磁盘 | 必须纳入共用存储修正，验证非默认 disk |
| 流已被读取但未复位 | Generator 第 87 行读完流后返回；下游能否再读受适配器是否 rewind 影响 | 补回归，确保所有返回流从起点可读；不直接断言每个磁盘必定空文件 |
| 文件指纹缺 page，固定 jpg | 第 32～33 行仅 scene/styles/env | 补 page；按真实内容处理扩展名，验证旧调用影响 |
| 验证回调类型不一致 | Rule 对缺 scene、非法 path 传字符串；Provider 回调只接受 Throwable | 修复字符串失败处理及 Validator 成败返回契约，不能把网页 URL 接到这个远程校验上 |
| 直接输出默认 env 与保存入口不一致 | `getQrcodeOutput()` 可传 null，handle 才补 release 默认值 | 微信回归时统一默认值行为并记录变动 |
| 新建记录早于生成 | HasQrcodes 先 create，再调用外部接口；失败可留未生成记录 | 新网页入口避免复制；旧微信失败生命周期改造另评估，不借机重写 |
| Trait 默认参数与生成器不一致 | disk 可取 null，而 handle 要求 string；path 直接索引 | 明确默认值，并覆盖省略 options 场景 |
| 内层回调未返回值 | Trait 写 urls 的回调无 return，外层 result 通常为 null | 文档澄清旧行为，新 API 返回固定模型，不无意改变旧回调契约 |
| 测试不足 | ExampleTest 仅断言 true，另有架构测试；没有生成、存储、迁移业务覆盖 | 必须补真实行为测试，不能以现有测试通过判断可上线 |

Provider 重复注册 Nova、未使用的字段和原有权限设计等不在本期顺手清理范围。与微信 API 错误处理有关的变更应有假响应测试，微信真实接口行为仍需实测。

预计涉及约 10～14 个生产代码/配置文件及新增迁移，另增加测试与使用文档。文件数随是否抽取存储辅助类调整；这不是把每个文件都重构的授权。

### 必须覆盖的验收矩阵

1. 普通 HTTPS URL、带查询参数和 fragment 的 URL，解码结果与输入逐字一致。
2. 拒绝空 URL、相对路径、javascript/data/ftp 等 scheme、带控制字符、超限输入；不发微信或目标站点 HTTP 请求。
3. PNG 可读、Data URL MIME 正确、静区完整；至少用独立解码器及真实手机各验证一组短 URL 与长 URL。
4. 默认磁盘、非默认磁盘、写入失败三种情形；失败不写 `urls`，不返回伪成功。
5. 同 scene 不同 page、同目标不同宽度、网页与微信之间文件不误覆盖。
6. 全新安装、旧迁移已发布、旧迁移未发布都升级成功；旧记录 type 正确且原图片 URL 保留。
7. 网页无需微信凭据生成；微信仍按原 env/page/scene 行为执行。包含 token 失效、微信 JSON 错误、可读流、Data URL 分支回归。
8. 网页目标更新使当前预览失效并提示重生成；不得暗示已印出的二维码自动更新。
9. Nova 类型不可修改、表单规则按类型生效、混合批量拒绝、队列执行正确；服务端不得绕过类型与授权约束。
10. 宿主真实微信登录与绑定各验收一次；离线 Mock 测试不能替代这一项。

测试使用指定 Herd PHP；包内当前无独立 vendor，默认 PHPUnit 配置依赖包内 `vendor/autoload.php`。开发阶段需先建立可用测试安装，不能把宿主 vendor 存在当成包测试环境已经准备好。至少验证 PHP 8.2 目标依赖解算与实际宿主版本；不扩大到所有 `illuminate >=10` 组合的全面兼容承诺。

## 7. 如果实际需要活码

二维码编码稳定的本站短链接，访问时服务端读取目标 URL，并检查启用状态和 expired_at，再跳转。修改目标无需重印二维码；但可用性依赖本站域名、应用和数据库长期在线。

额外开发包括不可猜测 token、公开跳转路由、停用/过期响应、禁止跳转缓存导致状态不生效、可信后台目标配置、访问限流，以及明确口径的访问事件统计。HTTP 访问量不等于独立扫码人数，不能直接包装成精确扫码人数。

活码的权限、统计留存、目标变更审计、域名与运营责任需要单独设计。本文的 3～5 人日不包含这些能力。

## 8. 实施范围与验证边界

- 实施范围已定为完整 Nova 静态码；短链接活码不包含在内。
- 项目允许类型设计已确认：使用 `allowed_types` 支持仅小程序码、仅网页二维码或两者都允许；建议默认值为两者，具体宿主项目通过配置收窄。
- 既有数据：建议按有历史记录设计新增迁移。若明确只做全新安装，可简化迁移方案，需重新确认后调整。
- 默认图片：建议黑白 PNG、无 Logo、沿用现有尺寸范围；其他物料需求另估。

实现过程中已通过类型配置与网页输入校验测试、PHP 语法和 Composer manifest 检查。由于新包依赖安装未能完成，真实 PNG 生成、迁移执行、完整 Pest 套件和 Nova 浏览器验收仍待验证；微信接口及宿主登录/绑定也未进行线上实测。本文是实现说明与未完成验证项，不代表这些项目已通过。
